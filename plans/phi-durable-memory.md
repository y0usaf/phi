## Goal — two things, nothing else

1. **Extremely durable execution** — absurd's replay discipline, faithfully ported to Phi's interactive TUI + JSONL/SQLite stack (no Postgres).
2. **A durable memory system** — ori-mnemos's memory model (three spaces, graph-aware forgetting, identity, recursive explore), made crash-safe and replay-safe.

Everything else (sandbox environments, visualizer, token-aware compaction, depth surfacing, training env) is out of scope for this plan.

## What "matches absurd" means — the key scoping decision

absurd's actual contract (quoted from `ref/absurd/docs/concepts.md`):

- *"once a step completes successfully, its return value is persisted … and the step will never execute again — even across process restarts or retries."*
- *"Code **outside** steps may execute multiple times across retries. Keep side-effects inside steps."*

**absurd does not checkpoint arbitrary code.** It checkpoints *named side-effecting steps* and explicitly lets surrounding code re-run. Therefore:

- **"Absurdly durable" for Phi = checkpoint every harness-observed side-effecting unit; let the turn-loop and model reasoning around them re-run.** The harness-observable side-effecting units are `rlm_query` sub-calls (spend LM budget) and **tool calls** (read_file / edit_file / bash / memory_* — real side effects).
- **Per-repl-block resume is *more than absurd promises*** (absurd says code outside steps re-runs). It stays an optional stretch goal, not the bar for "absurdly durable."
- This **un-defers run/retry**: absurd's retry = a new run that re-runs ordinary code and skips checkpointed steps — no per-block gating needed, so it is feasible exactly as absurd does it.

The guarantee, stated plainly: a side-effecting tool call or `rlm_query` sub-call that completed before a crash is **not re-executed** on resume (no re-spent LM budget, no re-applied file edit, no duplicate memory capture) — matched by **content identity**, so a *re-emitted identical* call skips while a *changed* call re-runs. The model's reasoning between calls and non-side-effecting repl code re-runs. That is absurd's "exactly-once for the important logical steps," adapted to Phi where (unlike absurd) the *model*, not the developer, sequences the steps: identity by content makes that adaptation safe.

### A2 — The checkpoint envelope around every side-effecting unit (L) — "match absurd"

The load-bearing change. absurd says keep side effects inside steps; Phi's harness-observable side-effecting units are `rlm_query` sub-calls **and tool calls**. Both become checkpointed, skip-on-replay steps.

**Step identity = the call's content, not a synthetic key.** A step's identity is its content: a `CallIdentity = { tool: String (or "rlm_query"), args: Value }` (for `rlm_query`, `args` captures the prompt/depth/params that define the sub-call). The checkpoint stores `(operation_id, CallIdentity, result)`. Skip-on-replay asks one question: *"is there a committed checkpoint for THIS exact call, in this operation?"* — yes → return the cached result; no → execute. There is no `step_name`, no `#index`, no ordering dependency. This is the decision that resolves the central gap the review raised: absurd's contract assumes the **developer** names steps deterministically, but Phi's **model** chooses the tool sequence — and on a retry the model can emit a *different* tool sequence. With position-based keys (`tool:edit_file#1`), a retried `edit_file#1` could target a *different file* and inherit a checkpoint it shouldn't. With content identity, a semantically different call simply does not match → it re-executes; an identical call matches → it's skipped. `rlm_query` sub-calls use the **same** `CallIdentity` mechanism (one identity model, not two), with `args` pinning the sub-call's prompt+depth. (A content hash on `CallIdentity` may be added later as a **lookup index only** if per-operation checkpoint counts make linear comparison expensive — it is an optimization, never a separate key concept.)

- **`DurableStep` envelope around `rlm_query`** (actual `phi-rlm/src/engine.rs:353-437` for `recurse()`; cited 366-451. `child.completion` actual `:420-422` [cited 433]; `handler.track_breakdowns` actual `:423` [cited 436]; the "cached return at `:450`" in the prior draft does not exist — `:450` is an unrelated brace in `notify_tool`, and no skip-on-replay path is present yet; this bullet describes the code to *add*. **L**) — `DurableJournal` wraps `append_durable` + the in-memory `DurableCursor`; thread `Option<Arc<DurableJournal>>` into `EngineSubcalls` alongside the existing `LmHandler`. `recurse()`: build the `CallIdentity` for the sub-call (tool=`"rlm_query"`, args = the prompt+depth+params); if `cursor.has(operation_id, &call_identity)` → return the cached `SubcallResponse::Text` **before** `child.completion` (skip — no child spawn, no `handler.track_breakdowns`, no budget re-spent); else emit `StepStart` before `child.completion`, run child, emit `StepCheckpoint{ operation_id, call_identity, result }` (serde'd completion) after. A crashed sub-call has `StepStart` with no `StepCheckpoint` → re-run only that one; identity-matching handles the retry-reorders-calls case automatically.
- **`ToolCallCheckpoint` for side-effecting tool calls** (emit path: thread through `notify_tool` → `loop_detector.observe_call` at actual `engine.rs:485`, with the `ToolResultEvent` emit at actual `phi-runtime/.../hooks.rs:237-247`. **`hooks.rs:66-75` is the `HookEvent` struct definition, NOT an emit site; `runtime.rs:201-214` is `invoke_tool_sync` (the dispatcher), not hook-based observation.** **L**) — the broadening that makes this *match absurd* rather than "sub-calls only." Extend the `ToolCallStart`/`ToolCallFinish` pair (A0) into a checkpointed step: emit `StepCheckpoint` with `call_identity = { tool: tool_name, args: <the tool input JSON> }` (content of the call, **not** `tool_name#index`), `result = ToolOutput.content`, and `operation_id`. On resume, a side-effecting tool call with a committed checkpoint for that exact `(operation_id, call_identity)` is **skipped** — its recorded result is returned to the model without re-executing the side effect (no double file edit, no duplicate memory write). Because identity is content, a retried model that re-emits the *same* `edit_file(path, content)` is correctly skipped, while one that changes `path` or `content` gets a cache miss and re-executes. Read-only tools (`read_file`, `grep`, `memory_recall`) may re-execute cheaply or skip per a per-tool policy (default: skip if checkpointed — they're deterministic enough and skipping is safe). **This is the "exactly-once for important logical steps" guarantee absurd sells**, extended to Phi's tool surface. Model-generated repl blocks are *not* checkpointed (matches absurd's "code outside steps may run multiple times") — a crash mid-repl re-runs that block; only the harness-observed tool/sub-call steps are protected.
- **Idempotency for side-effecting tools** (**M**) — `edit_file`/`bash`/`memory_capture` skip via the `(operation_id, call_identity)` checkpoint; on a retried run the cache short-circuits before the side effect. For tools whose side effects are external and not reversible (e.g. a future `bash` that sends an email), document that the idempotency identity must be carried to the external system (absurd's "external idempotency inside steps") — out of scope to implement now, but the identity is available.
- **Budget continuity across crash — idempotent apply** (**S**, folded into A2) — persist `usage` inside each `StepCheckpoint` and add checkpointed child usage to the parent's `UsageLedger` on resume (`LmHandler.usage` is a single shared in-memory `Mutex<UsageLedger>` across root + all sub handlers, actual `handler.rs:53-88`; cited `:65`). **The apply must itself be idempotent:** guard with an "already-applied" set of `(operation_id, call_identity)` so that a resume-of-a-resume (a second crash after a partial resume) does NOT re-add the same child usage and double-decrement the budget. Without this guard, budget continuity is false under chained crashes.

### A3 — Run / attempt + backoff at the operation level (M) — un-deferred

Now feasible because retry needs no per-block gating (absurd's model: a new run re-runs ordinary code, skips checkpointed steps).

- **Run orchestration** (lib.rs + engine.rs run path, **M**) — `RunStart` (attempt 1) → run the operation → `RunFinish` on success; on failure, `RunRetry` with `BackoffKind` (fixed/exponential/none) → new run (attempt 2) re-runs the turn-loop code and **skips checkpointed tool/sub-call steps** via A2's content-identity cursor. A retried attempt re-invokes the provider for a fresh completion (post-stream the transport refuses to retry at actual `provider.rs:140` — the `!streamed.load(...)` guard falling through to `return Err(e)` at `:146` — so a new `RlmCompletion` is required) and rebuilds history from the transcript + checkpoints. **Key property under retry:** the model may re-sequence its tool calls on a fresh completion. With content-identity this is handled correctly — identical calls hit the cache and skip; *changed* calls are cache-misses and re-execute. There is no `step_name#index` correlation to break. `StopCause::Prose` (defined at `config.rs:78`/`engine.rs:101`; nudge-then-accept logic at actual `engine.rs:819`/`1034-1055`/`1084-1086` run_loop — **NOT** in `loop_detect.rs`, which only emits `StopCause::LoopDetected` at its lines 9/101) accept is **non-retryable** (respects the locked RLM loop-termination decision). Capped attempt count + total budget from `RlmConfig`.

- **skip-on-replay (A2):** a checkpoint for `(operation_id, call_identity)` returns the cached result without spawning the child or calling `track_breakdowns`; on resume the checkpointed child usage is added to the parent's `UsageLedger`. A retried operation that re-orders its tool calls still skips the unchanged ones and runs the changed ones (no `#index` ordering to break).
- **idempotent budget apply (A2):** a resume-of-a-resume (crash after a partial resume) does NOT double-add checkpointed child usage; the parent's remaining budget is the same after the second resume as after the first.
- **run/retry (A3):** an operation that fails after step 1 completes, retried, skips the checkpointed call and re-runs from the next; `StopCause::Prose` is not retried.
- **replay-to-resume integration:** a fake turn writing `OperationStart`/`TurnStart`/`StepCheckpoint`×2 then crashing (no `OperationFinish`) → `recover()` → `ResumePlan` contains both committed `call_identity`s and the `unfinished_operation`; the resume cursor reflects that two calls completed.

### B4 — Memory-write idempotency (S)

- **Idempotent capture/link — dedup lives in the memory DB, not the session** (**S**) — the memory SQLite DB is already crash-safe (WAL, fsync), but a retried `memory_capture` after a crash could duplicate a note. **Dedup is self-contained in the memory DB:** the `memories` table gets a nullable `dedup_id TEXT` column with a partial `UNIQUE` index `CREATE UNIQUE INDEX idx_mem_dedup ON memories(dedup_id) WHERE dedup_id IS NOT NULL` (added in B0's migration alongside the space columns). `capture`/`link` stamp `dedup_id` with the **same `CallIdentity`** A2 uses (operation_id + the call's content — full call, or its hash) when invoked under a durable operation. The insert is `INSERT ... ON CONFLICT(dedup_id) DO NOTHING` and returns the existing row's id on collision. This survives a crash that **loses the session checkpoint entirely** — even if A2's session-side cursor is gone on resume, the memory DB itself rejects the duplicate. **Critically, the dedup key is the call identity, not a session-side `(operation_id, step_name)`** — because the memory DB has no notion of `step_name`, and the dedup must not depend on the session StateDb (which may be absent/corrupt per A1's cache-only stance). Read-only tools (`memory_recall`/`memory_explore` Phase-1 PPR) carry no `dedup_id` and re-execute safely. This closes "durable memory system": data is crash-safe (SQLite WAL), operations are replay-safe (A2 steps), writes are idempotent (B4, in the memory DB).

## Non-goals / locked decisions preserved

1. **NO native provider `tool_use`; tool-call turns are ```repl``` code fences only.** Tool/sub-call steps are harness-side checkpoints keyed by **`CallIdentity` (the call's content)** — invisible to the model. The model reaches tools as repl-fence stubs; durability wraps the harness's *execution* of them, not a provider tool protocol.
2. **Interactive mode is "TUI mode", never "chat mode".** An operation/run is a single in-flight TUI prompt's execution attempts; no background chat worker. absurd's pull-based multi-worker/queue/lease model is **deferred** (single-user interactive TUI does not benefit from it) — only the replay *discipline* is ported.
3. **Rust-first, `nix develop -c cargo`; extensions behind the capability ABI (phi-ext/phi-runtime), not a generic MCP server.** `StateDb`/`EventCache` are native Rust SQLite (consistent with phi-memory's precedent). No MCP server for memory/durable tools.
4. **Memory vault is SQLite+FTS5; tools are native Rust handlers surfaced as Python stubs.** No full bidirectional markdown vault (export + one-way import only; SQLite canonical). B4's `dedup_id` column + partial UNIQUE index are *part of the memory DB schema* — memory-write idempotency is self-contained in SQLite, not delegated to the session StateDb. The phi-memory DB is not extended into a session-state DB (separate `StateDb`). Ranking (`fusion_rank`) untouched.
5. **`rlm_query` recursion is trait recursion on `LanguageModel` capped by `max_depth`, budget/time deltas inherited.** A2's `DurableStep` envelope wraps this existing path; no new recursion mechanism. Both `rlm_query` sub-calls and tool calls checkpoint by the same content-`CallIdentity` model (one identity mechanism, applied to two step kinds). Memory's recursive explore is a separate bounded loop (B2), not fused to `rlm_query`, and runs only on the tool path.
6. **Session durability is append-only JSONL with a tolerant reader; the reducer is authoritative. NO Postgres.** `StateDb` is a rebuildable-from-JSONL **cache** (JSONL-fsync-first, then SQLite-commit) consulted for cross-run inspection only — **never** for a resume/skip decision, which always runs `reduce_log(JSONL)`. absurd's PLpgSQL/t_/r_/c_/e_ tables and `FOR UPDATE SKIP LOCKED` lock ordering are translated to per-session SQLite tables / single-writer txn. New line types are skipped by old readers, reduced by new ones.

**Out of scope (this plan):** rlm sandbox environments, visualizer trajectory recorder, token-aware compaction, depth surfacing into the prompt, training/verifiers env, the full bidirectional markdown vault, all fusion/ranking work (embeddings/RRF/intent/dampening/spreading-activation/UCB/NPMI/LinUCB), the **async-to-sync owner-task bridge** (recursive explore instead runs only on the tool path; see B2 / Risk #4), per-repl-block env-exec-skip (more than absurd promises — optional stretch goal; the discard site is `session.rs:700-707`, not the engine), the phi-task pull-based worker.

## Risks & open questions

1. **Per-repl-block resume — optional stretch, not the bar.** It exceeds absurd's own contract ("code outside steps may run multiple times"). If you later want a crash mid-Python to resume mid-Python, it needs positional correlation in `branch_restore`/`RestoredExchange` — the `ReplEntry.id` (+ parent_id/timestamp/duration/tools/subcalls) is dropped in the `RestoredRepl { code, stdout, stderr }` conversion at **actual `phi-session/src/session.rs:700-707`** (`branch_restore`'s `restored()` closure) — NOT at `engine.rs:1854-1871` (that is `shutdown()`/`history_snippet`; the *receiving* structs `RestoredRepl`/`RestoredExchange` are at `engine.rs:1883-1898`). A real but larger piece of work. Recommended: leave it out unless interactive resume fidelity becomes a felt problem; the A2 tool/sub-call guarantee already covers the expensive/side-effecting work.
2. **Side-effecting-tool step policy.** Which tools are "side-effecting" (skip-on-replay) vs "read-only" (may re-execute)? Default: `edit_file`/`bash`(write)/`memory_capture`/`link` skip; `read_file`/`grep`/`memory_recall` skip-if-checkpointed (safe, deterministic). `bash` is the subtle one — a bash command can be side-effecting or not; treat all `bash` as side-effecting (skip-on-replay) to be safe, accepting that a pure `ls` might return a stale result on resume (documented). **Note:** since step identity is the call *content* (A2), a checkpointed `ls` skips and returns the stale listing — flagged here, but the content-identity model means a *changed* bash call always re-runs, so staleness is bounded to byte-identical re-emissions.
3. **Budget continuity across crash.** Solved by persisting `usage` in `StepCheckpoint` and adding checkpointed child usage to the parent's `UsageLedger` on resume (A2 fix). Without it the checkpoint skips the re-run but total spend is unrecoverable (`LmHandler.usage` is in-memory only). **The apply is idempotent** (guarded by an already-applied set keyed on `(operation_id, call_identity)`) so a resume-of-a-resume does not double-decrement the budget.
4. **The `block_in_place` runtime-context hazard (B2) — RESOLVED by split, not by a bridge.** Sync memory tool handlers are reachable from worker threads (OK) and `spawn_blocking` slash commands (PANIC). Rather than an owner-task bridge, B2 runs recursive decompose **only on the `memory_explore` tool path** (worker thread, `block_in_place` safe) and gives `/explore` (spawn_blocking) the non-recursive Phase-1 PPR. No bridge is built; the hazard has no surface. (The earlier plan's fallback becomes the spec.)
5. **SessionStart plumbing.** B1 (differentiated decay + bridge protection) is gated on A0's `start_session` wiring. It is a pre-existing dead-path fix (confirmed: zero non-test callers of `start_session()` repo-wide; def at actual `runtime.rs:127`, cited `:125`; `boot()` is at `session_builder.rs:100`, cited `:106`).
6. **Run/retry vs the locked loop-termination decision.** `StopCause::Prose` accept must be non-retryable (the locked nudge-then-accept behavior at actual `engine.rs:819`/`1034-1055`/`1084-1086` run_loop — **NOT** in `loop_detect.rs`, which only emits `StopCause::LoopDetected`). A3 retries only genuine failures, never a prose-accepted turn.
