# Phi three-way synthesis: rlm engine × ori-mnemos recursive memory × absurd durable execution

## Thesis

Phi is already a partial mix of its three references. **phi-rlm *is* rlm's engine** — the recursive `rlm.completion` completion loop, the ```repl```-fence / `answer["ready"]` protocol, `llm_query`/`rlm_query` sub-call routing, depth-based routing with budget/timeout inheritance, and the `RlmEvent` observability stream all already ship. **phi-memory *is* ori-flavored** — PPR, ACT-R decay, Q-values, wiki-link edges, and the seven memory tools already exist. **phi-session *is* proto-durable** — `DurableEntry` + `RecoveryReducer` + `RecoveryReport` (`crates/phi-session/src/durable.rs:24-136`) is an append-only, fsync-per-line JSONL event log with a tolerant reader that already skips unknown type tags. This plan closes the gaps so Phi becomes the faithful *combined* realization of the three, unified by **one recursion model** (memory recursion and RLM recursion become the same `EngineSubcalls::recurse` code path, checkpointed as absurd steps) and **one event-sourcing layer** (identity auto-inject, durable turn-replay, and recursive-sub-call checkpoints all flow through the single `phi-session` JSONL log + one `SystemPromptMod` injector).

**Scope note — memory ranking is out of scope.** This plan does *not* touch `phi-memory`'s existing ranking function (`fusion_rank` at `store.rs:273`, BM25+PageRank+ACT-R+warmth+strength+recency). ori-mnemos's "fusion"/retrieval-intelligence layers — embeddings/semantic signal, RRF, intent-adaptive weights, dampening, spreading activation, decayed-Q/UCB-Tuned reranking, NPMI co-occurrence, LinUCB — are intentionally **omitted**. The ori ideas this plan *does* take are the two that are not about ranking: **differentiated forgetting** (three memory spaces with different decay rates, bridge-protected) and **recursive exploration** (decompose → recurse, unified with rlm's recursion). Existing recall ranking stays exactly as-is.

## The three reference souls

### rlm — Recursive Language Models

RLM is a `CodeAct` system that replaces the canonical `llm.completion(prompt, model)` call with `rlm.completion(prompt, model)`, treating the language model itself as a recursive primitive: context is offloaded as a variable in a REPL (not fed through the context window), and sub-LM calls are *functions in code* rather than JSON tool-calls. Its essence is recursion as a first-class operation — `rlm_query()` spawns a child RLM with its own REPL+namespace, recurses to `max_depth`, and falls back to a plain `llm_query` at the leaf, with children inheriting the *remaining* budget/timeout. The orchestrator-not-solver ethos is load-bearing: "As an RLM, you should act as an orchestrator, not a solver" — the root must push long-context work into sub-calls and reserve its own tokens for high-level decisions. Completion is signaled by a sentinel dict mutation, not a tool return — "`answer[\"ready\"] = True`; the env surfaces the content on REPLResult.final_answer once ready flips truthy," and the harness restores all reserved scaffold names after every cell so model code cannot corrupt its own environment.

### ori-mnemos — Recursive Memory Harness (RMH)

RMH is a 6-layer cognitive memory system whose three constraints define it: "(1) Retrieval must follow the graph — notes are nodes, wiki-links are edges, PPR + spreading activation; (2) Unresolved queries must recurse — sub-question decomposition with convergence detection (ori explore); (3) Every retrieval must reshape the graph — co-occurrence edges grow, Q-values update, the graph learns from use." Its distinctive moat is graph-aware forgetting: ACT-R base-level decay plus spreading activation plus Tarjan articulation-point bridge protection — "No shipped system has graph-aware forgetting. Ori is first." Decay is architecturally differentiated across three spaces — "Identity (self/) decays at 0.1x — barely fades. Knowledge (notes/) decays at 1.0x — lives and dies by relevance. Operations (ops/) decays at 3.0x — burns hot and clears itself." Retrieval is navigation, recursion, and learning — not search: "RMH treats retrieval as navigation, recursion, and learning — on a graph that evolves with every session." *(This plan takes the differentiated-forgetting and recursive-exploration ideas from ori; the fusion/retrieval-intelligence ranking layers are out of scope — see Scope note above.)*

### absurd — durable-execution workflow engine

Absurd is a Postgres-native durable-execution engine where all durable behavior lives in PLpgSQL stored procedures and SDKs are intentionally thin callers. Its central idea is that replay is *not* a deterministic workflow runtime — "In Absurd, the system replays a task by **reusing checkpoints** and re-running ordinary code around them." A crashed task resumes by re-running the ordinary handler from the top while short-circuiting steps whose checkpoints already exist: "once a step completes successfully, its return value is persisted in Postgres and the step will never execute again — even across process restarts or retries." It is pull-based with no coordinator — "There is a no push mechanism and no coordinator service" — and its event cache is race-free via a NULL→JSON transition: "Events are cached (first emit wins), which means they are race-free." Retries are task-level with fixed/exponential/none backoff, and "Running tasks detect cancellation at the next checkpoint write or heartbeat call and stop gracefully." *(This plan ports absurd's replay-by-reusing-checkpoints and first-emit-wins *ideas* onto Phi's existing SQLite/JSONL stack; the PLpgSQL schema and pull-based workers are not adopted — see Non-goals.)*

## Architecture: how the three compose

The composition design (`area === "composition"`) names four existing Phi seams that are **not renamed**, only extended. Three shared types/traits carry the unification:

1. **`DurableJournal`** (new, thin) — wraps `SessionStore::append_durable` (`session.rs:332-363`, the single append+fsync chokepoint) plus an in-memory `DurableCursor` built by `RecoveryReducer` from `StepCheckpoint` lines. Threaded as `Option<Arc<DurableJournal>>` into `EngineSubcalls` alongside the existing `LmHandler`. The journal is append-only JSONL; durability/fsync is inherited.
2. **`SubcallRequest::Explore { query, depth }`** (new variant) — dispatched by `EngineSubcalls::handle` to `recurse()` with a synthesized decomposition prompt, so memory recursion rides the *same* `EngineSubcalls::recurse` path (`engine.rs:366`) as `rlm_query`, inheriting the same depth/budget/timeout deltas and the same `DurableStep` envelope.
3. **`EventReturn::SystemPromptMod`** (already exists, `event.rs:92`, spliced in `filter_system_prompt` at `runtime.rs:62-89`) — the single system-prompt injection vehicle. Identity, recalled memories, and resume-context are three independent `BeforeAgentStart` handlers whose `SystemPromptMod` returns `filter_system_prompt` already concatenates (prepend before, append after, in handler-iteration order). No new splicing mechanism.

**(a) `rlm_query` sub-calls become durable checkpointed steps.** `EngineSubcalls::recurse` (`engine.rs:366-451`) already spawns a child Rlm at `next_depth` with remaining budget/timeout inherited (`engine.rs:379-400`). The `DurableJournal` brackets that same path: before `child.completion` (`engine.rs:433`) the harness emits `StepStart{ operation_id, depth, step_name=rlm_query#N, prompt_hash }`; after (`engine.rs:442`) it emits `StepCheckpoint{ ... state: serde'd completion }`. On replay, `recurse` consults the `DurableCursor` first; if a committed checkpoint exists for that `step_name` with `attempt <= current`, it returns the cached `SubcallResponse::Text` at `engine.rs:450` without spawning the child or calling `handler.track_breakdowns` (`engine.rs:436`) — LM budget is genuinely not re-spent. A reclaimed/crashed sub-call has a `StepStart` with no `StepCheckpoint`, so resume treats it as incomplete and re-runs only that one step. The `step_name` is the absurd-style auto-numbered `rlm_query` / `rlm_query#2` (dedup counter keyed by `(operation_id, depth, step_name)`); the serialization contract is `operation_id + depth + "rlm_query#N"` so emit-time and cursor-lookup keys match exactly.

**(b) Recursive explore IS an `rlm_query` sub-call** — unifying the two recursion models. `memory_explore` no longer calls `store.explore` flat. `ExplorePlanner` (Rust, lives in phi-memory) drives a loop of *decompose → recurse ONE sub-question → collect `memory_recall` results via a visited set → check convergence*; each iteration calls `recurse()` once with a synthesized decomposition prompt. Because this routes through `SubcallRequest::Explore → EngineSubcalls::handle → recurse()`, the depth/budget/timeout inheritance and the `DurableStep` envelope from (a) apply automatically — memory recursion and RLM recursion are literally the same code path. The fallback (when `max_depth <= 1` or recursion is disabled) branches *before* `recurse()` and calls `store.explore_seeds()` (the renamed PPR) and returns — **not** a plain LM completion (recurse at `max_depth` does `self.query` → a plain LM call that does no memory recall, so it must be bypassed explicitly). This guarantees `explore ⊇ flat` and the deterministic Phase-1 path is the no-op-fallback.

**(c) Memory auto-inject + durable turn-replay share the `phi-session` event layer.** Identity becomes a durable fact: the `before_agent_start` handler (`events.rs:8-58`) deterministically pulls an identity memory and renders it as a `SystemPromptMod` append; the identity memory id and rendered block are written as `DurableEntry::IdentityInjected{ id, timestamp, session_id, identity_memory_id, block_hash }` so the exact prompt augmentation is part of the durable record and replays deterministically. The dead `PhiHarness::recover` (`lib.rs:353-386`) is wired to startup and consumes `RecoveryReport.unfinished_operation` + `resume_cursor` + `pending_writes` to drive a "resume from step N" instead of re-running everything. (The stronger claim — gating `restore_session` env.exec per REPL on the cursor — was refuted and is omitted; see §Risks #4.)

**(d) Identity + recalled memories + replayed-prior-turn-state splice into the system prompt via one `SystemPromptMod`.** `filter_system_prompt` (`runtime.rs:62-89`) already iterates all returned `SystemPromptMod` and applies each prepend/append (`runtime.rs:78-87`), so three independent `BeforeAgentStart` handlers compose with no new mechanism: (1) identity handler emits `SystemPromptMod{ append: persona block }` from the identity memory; (2) the existing `make_before_agent_start_handler` emits `SystemPromptMod{ append: "## Recalled memories" }` (`events.rs:52`), now ordered AFTER identity via registration order in `extension.rs:62-66`; (3) a new `builtin.session.resume-context` handler reads the `DurableCursor`'s last completed step + the compacted `session_summary` (`engine.rs:1792`) and emits `SystemPromptMod{ prepend: "Resuming from step N; prior turn summary: ..." }`. Ordering is deterministic because `RegistryHost.event_handlers` is a `Vec` iterated in insertion order (`host.rs:14`); the plan asserts and tests the required order (identity, then recalled memories, then resume summary). The depth/env metadata currently not surfaced (`QueryMetadata` at `metadata.rs:6` omits depth) is folded in here as a small depth-inject append, closing the "depth not injected into prompt" gap.

### Non-goals / locked decisions preserved

The six Phi locked decisions govern every phase. Each line states what it rules out.

1. **NO native provider `tool_use`; tool-call turns are emulated via triple-backtick ```repl``` code fences only.** Rules out: modeling steps as provider tool-call turns (steps are REPL blocks / prelude tool handlers keyed by `step_name`); Option A explore sentinel→`rlm_query` back-channel (composition-b hard-rejects it); extending `ToolParam` (`tool.rs:16`) toward `input_json_schema`; any native tool_use schema generation from `ToolSpec`. The durable subcall is invisible to the model — a harness-side wrapper around `recurse()` surfaced identically as `rlm_query` in the repl. New tools (incl. `explore_recursive`) reach the model as repl-fence stubs via `__phi_ext_tool__` (`runtime.rs:218`) or host-fn shims (`driver.py:303-320`).
2. **Interactive mode is "TUI mode" (phi-mux/phi-tui), never "chat mode".** Rules out: run/task terminology implying a background chat worker (an operation/run is a single in-flight TUI prompt's execution attempts); the pull-based multi-worker task model (deferred to phi-task); any "chat" naming. The visualizer recorder is a background trace writer, not a chat surface.
3. **Rust-first workspace built via `nix develop -c cargo`; extensions ship as Rust (phi-builtins) or Lua (phi-lua) actors behind a capability ABI (phi-ext/phi-runtime), NOT a generic MCP server by default.** Rules out: an MCP server for memory/durable tools (composition adds durable behavior behind the existing `Extension`/`EventHandlerRegistration` ABI and `AppRuntime`); Python-SDK crates for sandboxes (`DockerRepl` shells out to the `docker` CLI — a runtime dep, not a build dep; if absent, `start()` fails with a clear `ReplError`, never at compile time); `EventCache` as a native Rust SQLite store (consistent with phi-memory's "native Rust handlers through the ABI" pattern); `StepContext` is a Rust trait in phi-session. Lua tools have no `phi.register_tool` path yet (no model-facing Lua tools) — out of scope.
4. **Memory vault is SQLite+FTS5 (phi-memory); tools are native Rust handlers behind the ABI, surfaced as Python stubs in the repl prelude.** Rules out: the full bidirectional markdown vault as source of truth (export enhanced + one-way `import_markdown` for seeding only; SQLite canonical; no filesystem watcher); extending the phi-memory SQLite DB into a session-state DB (separate sibling `StateDb` with a separate lifecycle); Postgres. provider embeddings is opt-in where used (out of this trimmed plan). The existing `fusion_rank` ranking function is intentionally left untouched (Scope note).
5. **Recursive sub-calls (`rlm_query`) are trait recursion on `LanguageModel` capped by `max_depth`, with budget/time deltas inherited by children.** Rules out: a new recursion mechanism; `RunController` (when it lands) reads the same `RlmConfig` and applies the same remaining-budget/remaining-time compute as `recurse()` (`engine.rs:377-400`). Memory-internal explore recursion is a separate bounded loop consistent with this lock's scope (governs `rlm_query` specifically); via composition-b it becomes an `rlm_query` sub-call inheriting the deltas. `Rlm` does NOT impl `LanguageModel` — recursion stays through `EngineSubcalls` (`engine.rs:317/513`), not trait self-calls.
6. **Session durability is append-only JSONL event sourcing (phi-session) with a tolerant reader that skips unknown type tags. NO Postgres.** Rules out: SQLite-as-source-of-truth (JSONL stays canonical; `StateDb` is a rebuildable-from-JSONL index — `StateDb::rebuild_from_log` reconstructs it if missing/corrupt; write order is JSONL-fsync-first then SQLite-commit); Postgres PLpgSQL/t_/r_/c_/e_/w_/i_ tables (translated to per-session SQLite tables); `FOR UPDATE SKIP LOCKED` + `FOR SHARE` lock ordering (SQLite single-writer txn — no row-level locks needed); the pull/claim/lease worker model (deferred to phi-task). The tolerant reader is extended, not replaced: new line types are skipped by old readers and reduced by new ones.

## Risks & open questions

The open decisions surfaced in `locked_decision_risk` and the verdict fixes, one line each + the recommended resolution. (Fusion/embedding/intent/dampening/UCB risks are intentionally absent — those changes are out of scope.)

1. **phi-task pull-queue in-scope vs deferred.** **DEFERRED.** **Recommended:** ship the `operation_id`-generic `StepContext` trait seam now (keyed by `operation_id`, not "the current prompt") so a future phi-task `ClaimedTaskContext` is not blocked; do not build the worker. The pull model's value (horizontal scale, no coordinator) does not pay off for single-user interactive TUI.

2. **The model-facing `step()` surface for naming model-generated repl blocks as checkpoints — UNRESOLVED.** The `DurableStep` envelope (composition-a) is harness-side around `recurse()` (`rlm_query` sub-calls), invisible to the model. Naming arbitrary model-generated ```repl``` blocks as durable steps requires either a positional `step_name` correlation in `branch_restore`/`RestoredExchange` (`engine.rs:1854-1871`, which discard `ReplEntry.id`) or a model-emitted step-name protocol — both larger than this plan's scope and the reason absurd-3 / composition-c-ii were refuted. **Recommended:** defer; revisit if durable per-repl-block resume is needed, and key `ResumePlan.checkpoints` by exchange-position then. In the meantime, gate the durable *operation* replay on step checkpoints (the seam that already matches) rather than env-exec-skip.

3. **Budget continuity across crash.** `LmHandler.usage` is in-memory only (`handler.rs:65`) and not restored. The `DurableStep` checkpoint skips re-run of completed sub-calls but does NOT by itself reconstruct total spend. **Recommended:** persist usage in `StepCheckpoint.state` and add checkpointed child usage to the parent's `UsageLedger` on resume (composition-a fix) — a narrower-than-full but honest guarantee ("skip-completed-steps for budget" is correct only with this addition).

4. **SessionStart / SessionShutdown plumbing.** Multiple ori changes (L1-1 deferred, L6 identity wired in Phase 4) depend on a live `SessionStart` handler + `current_session_id` on `MemoryStore` for the L6 `list_by_space` identity pull. **Recommended:** the Phase-0 wiring fix (`runtime.start_session()` after `boot()` at `session_builder.rs:106`) unblocks these; this is a pre-existing dead-path fix (no non-test caller of `start_session()` exists; `shutdown_session` is called only from `tui.rs:1462`).

5. **System-prompt splice ordering depends on handler-registration order in a `Vec` (`host.rs:14`).** A future extension reordering registration could interleave identity/recall/summary wrongly. **Recommended:** document and assert the required order (identity, then recalled memories, then resume summary) in `extension.rs` and add a registration-order unit test; do not change the splicing mechanism itself (composition-d verdict).
